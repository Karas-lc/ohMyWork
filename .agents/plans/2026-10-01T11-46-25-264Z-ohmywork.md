用户批准同步第二轮访谈决定，仅修改文档，不创建 Rust 工程或运行功能测试。

1. **内容结构**：仅一个 Workspace，真实 Atlas/、Efforts/、Archive/ 目录；项目/领域只是 Efforts 下的普通文件夹。撤销多 Workspace 注册、切换和跨库设计。
2. **本地数据**：自动创建 `.ohmywork/id`；其余默认 `%LOCALAPPDATA%\ohMyWork\`，一个全局 SQLite 索引；便携模式才额外写可迁移状态。
3. **发现与搜索**：专有 `.ohmyworkignore`，不读 `.gitignore`；按系统语义跟随符号链接并防循环；文件名/Markdown 正文搜索，Archive 默认不搜索/汇总，可显式纳入。
4. **Markdown**：CommonMark + GFM，纯可视化，无 Live Preview/源码模式；Raw 节点保留未知原文；最小范围改写。
5. **链接**：普通可点击链接，相对文件路径和 Workspace 根路径；不做标题 slug、反向链接、重命名引用更新。
6. **正文保存**：Ctrl+S；关闭脏内容保存/放弃/取消；无未提交恢复草稿。真实外部修改直接丢弃本地未保存编辑，无恢复。安全写入采用同目录临时文件 + 原子替换。
7. **任务保存**：组件操作立即只写目标任务，其他脏正文保留并合并内存状态；必须区分宿主自写与外部修改。
8. **基础 Task**：checkbox、标题、start/due 日期（YYYY-MM-DD）、priority 1–9（9 最高）；没有独立 status、时间、时区、重复或依赖。
9. **版本**：V2 插件/资源/自动化/Dataview；日历和 ICS 放 V3，原 V1 iCalendar 契约撤销。
10. **界面**：一个主窗口，嵌套横纵 Pane、标签/布局/滚动恢复但不恢复脏正文；Homepage 无限画布，可平移缩放，有可删除起始布局。无日历/多 Workspace 组件。
11. **预览**：图片与 PDF 内置只读预览，无编辑/批注/OCR，其余外部打开。
12. **Pi**：PATH + 用户路径/命令；用户自行指定 cwd、选择新建/恢复，不固定唯一会话。官方 RPC 原生侧栏/Extension UI，关闭 abort 后退出；视觉收起边界待定。文件传路径、选区传文本，不自动注入内容，也不干涉 Pi 队列/插话/工具配置。
13. **个性化**：主题仅手动导入原始副本到 LocalAppData，关键 Token 自动安全覆盖并展示修正；默认快捷键 + keymap.jsonc；简体中文与英文。
14. **分发与诊断**：Windows 11 x64，当前用户安装包、手动升级；仅本地日志与主动导出，默认无正文/Pi 对话/凭据，不做遥测。

## 以下为 2026-10-01 历史检查点（非当前执行规格）

## 1. 产品定义

### 1.1 愿景

ohMyWork 是一个可分发的、本地优先的个人生产力工作站。它应当主动适配用户已经在使用的工具、人员与流程，而不是要求协作者改变工作方式；目标是尽快把尽可能多的可用资源组织并投入实际产出。

它不是团队协作平台，也不是 Obsidian 的克隆。

### 1.2 核心体验

- Windows 原生桌面应用。
- 主体语言为 Rust，界面使用 Zed 团队的 GPUI。
- 以极致响应性能为基础，面向高强度、键盘优先的工作流。
- 使用本地 Markdown 文件作为主要内容事实来源。
- 提供全局 Homepage、多工作区、标签页、分栏、链接、搜索和命令面板等工作站交互。
- 通过官方 Pi RPC 接入用户已经安装和配置的 Pi Agent。
- 后续通过独立进程插件聚合和调度浏览器、邮箱、微信、飞书等外部产品，但不尝试替代它们。

### 1.3 产品原则

1. **适配现有工作流**：不要求协作者或外部系统迁移到 ohMyWork。
2. **本地优先**：核心功能无账号、无必需云服务并可离线运行；网络只服务于用户主动启用的集成和 AI。
3. **开放文件**：人工创作内容保持为普通 Markdown；可重建索引不成为事实来源。
4. **稳定边界**：跨产品能力使用版本化、可协商的 JSON 契约，载荷和传输解耦。
5. **性能是产品能力**：启动、输入、导航、搜索和布局更新必须保持可感知的即时响应。
6. **不干涉用户 Pi**：ohMyWork 兼容用户环境，不治理、修复或重写用户的 Pi 配置。

## 2. 版本范围

## 2.1 V1：本地工作台 + Pi

V1 包含：

- Windows 原生 Rust/GPUI 应用。
- 任意本地目录作为工作区。
- Markdown 页面与 Obsidian 式 Live Preview。
- 文件树、标签页、分栏、页面链接、搜索、预览和命令面板。
- 可配置的全局 Homepage。
- 本地任务与日历。
- 显式 ICS 导入与导出。
- 用户现有 Pi 的 RPC 集成。
- Zed 主题导入与应用级主题系统。
- 本地状态持久化、恢复与可重建索引。

V1 明确不包含：

- 浏览器、邮箱、微信、飞书连接器。
- 通用插件宿主。
- 统一外部资源信封。
- 自动化规则引擎。
- 完整 Dataview 查询或 DataviewJS 执行。
- 跨平台交付承诺。

## 2.2 V2：资源、自动化与插件

V2 计划包含：

- 独立进程插件宿主与 SDK。
- 浏览器、邮箱、微信、飞书等连接器。
- 全局资源库、统一资源信封和来源原始载荷。
- 自动化规则与权限模型。
- Dataview 功能级兼容。

## 3. 产品与视觉基线

### 3.1 产品语域

- Register：`product`
- 品牌性格：**精确、迅捷、克制**。
- 借鉴 Zed 的交互密度、面板组织经验和主题加载体验，但不照搬其信息架构。
- 首要 anti-reference：网页 SaaS 仪表盘。避免满屏圆角卡片、营销式大数字和低密度留白。
- 同时避免 Zed/Obsidian 换皮、玻璃拟态、霓虹 Cyberpunk、无意义动画和持续发光效果。

### 3.2 无障碍

V1 目标为 WCAG 2.2 AA，并采用键盘优先设计：

- 正文文本对比度至少 4.5:1。
- 所有主要流程可通过键盘完成。
- 焦点状态明确且不只依赖颜色。
- 支持 Windows DPI/文本缩放。
- 支持减少动态效果。
- 状态、优先级和错误不能仅通过颜色表达。

## 4. 工作区与文件

### 4.1 工作区

- 用户可以直接打开任意现有目录，不导入、不复制、不要求位于应用管理目录。
- Markdown 原地读写，外部工具与 Pi 看到同一批文件。
- 默认将工作区状态保存在全局应用数据中，不污染现有目录。
- 用户可显式开启便携模式，在工作区创建 `.ohmywork/`，使布局和工作区设置随目录迁移。
- 全局 Homepage 聚合多个工作区。

### 4.2 Markdown

- 普通 `.md` 文件是页面事实来源。
- V1 使用 Obsidian 式 Live Preview，而不是纯源码/独立预览或完全所见即所得。
- Pi 与外部编辑器对文件的修改必须能够被检测并反映到界面。

待定：

- Markdown 方言及 CommonMark/GFM/Obsidian 扩展边界。
- Live Preview 的语法隐藏规则、光标行为和降级模式。
- Wiki Link、标准 Markdown Link、嵌入、标题块引用和反向链接的精确语义。
- 外部修改冲突、原子保存、自动保存和恢复策略。
- 大文件与超大工作区的降级策略。

## 5. Homepage

- Homepage 是全局、多工作区的可配置行动入口。
- 用户通过图形界面配置组件。
- 布局状态由应用内部持久化。
- 版本化 JSON 只用于导入、导出和迁移，不是实时配置事实来源。
- V2 插件可复用该布局契约，但 V1 只有内置组件。

V1 内置组件：

- 工作区列表。
- 最近页面。
- 置顶页面。
- Pi 会话。
- Pi 运行状态。
- 快捷动作。
- 本地任务。
- 本地日历。

待定：组件网格约束、尺寸档位、键盘重排、空状态、默认布局和损坏布局恢复。

## 6. 本地任务与日历

### 6.1 任务事实来源

- 任务是 Markdown 复选项，不是独立数据库记录。
- SQLite 仅保存可重建索引和界面状态。
- 任务元数据采用 Dataview 内联字段外形：`[key:: value]`。
- 不使用 Emoji 元数据。
- 字段名直接采用 iCalendar 属性名称，语义优先遵循 iCalendar，而不是 Obsidian Tasks 的自定义行为。

示意（最终值格式仍待确认）：

```md
- [ ] 提交方案 [uid:: ...] [dtstart:: ...] [due:: ...] [rrule:: FREQ=WEEKLY;BYDAY=MO] [status:: NEEDS-ACTION] [priority:: 5]
```

### 6.2 标准边界

- 任务与日历交换以 RFC 5545 的 `VTODO`、`VEVENT`、`RRULE` 为核心。
- 任务关系以 RFC 9253 的扩展关系为方向。
- `DTSTART` 定义重复集合的首个实例；RRULE 必须与 DTSTART 同步。
- V1 支持核心时间/状态、重复和依赖，而非仅保存字段。
- 未识别字段应原样保留，避免破坏其他工具的数据。

### 6.3 ICS

- V1 支持用户显式导入和导出 `.ics`。
- V1 不监听外部 ICS 文件，不做双向自动合并，也不直接同步 Outlook/Google/系统日历。

待定：

- Markdown 中 DATE/DATE-TIME、时区和浮动时间的文本编码。
- `UID` 生成及跨工作区唯一性。
- `RELATED-TO`/RFC 9253 在 Dataview 字段中的文本表达。
- 重复任务完成后是生成新行、更新原行还是维护异常实例。
- `RECURRENCE-ID`、`EXDATE`、`RDATE`、遗漏实例和修改单次实例的处理。
- 依赖阻塞、循环检测、跨文件/跨工作区引用规则。
- ICS 导入时对不支持属性、附件、参与者、闹钟和事件冲突的处理。

## 7. Dataview 兼容路线

### 7.1 V1

- 能解析并无损保留 Dataview 内联字段。
- 核心任务/日历只解释已定义的 iCalendar 对应字段。
- Dataview 查询代码块和 DataviewJS 不在 V1 执行；具体占位与错误展示待定。

### 7.2 V2

目标是 **Dataview 功能级兼容**：

- 元数据索引。
- `TABLE`、`LIST`、`TASK`、`CALENDAR`。
- DQL 数据命令、表达式和函数。
- 内联 DQL。
- 主要 `dv`、`dv.io` 和渲染 API。

明确不承诺：

- Obsidian `app` API。
- 浏览器 DOM 等价环境。
- 任意其他 Obsidian 插件 API。
- 与依赖 Obsidian 私有运行时的 DataviewJS 脚本逐行为一致。

兼容目标需锁定到明确的 Dataview 上游版本，并建立上游样例/测试夹具；版本尚待决定。

## 8. Pi Agent 集成

### 8.1 运行边界

- 使用用户自行安装的官方 Pi。
- Rust `Agent Gateway` 启动并监管 `pi --mode rpc` 子进程。
- 通过严格 LF 分隔 JSONL 的 stdin/stdout RPC 通信。
- stderr 作为诊断流单独消费。
- 必须持续消费 stdout，处理背压、异步响应 ID 和事件流。
- `prompt` 被接受不代表完成；`agent_settled` 是进入空闲/完成状态的权威事件。

### 8.2 非干涉原则

ohMyWork：

- 不内置、下载、升级、修复或修改 Pi。
- 不修改用户的模型、认证、Extensions、Skills、Prompts、工具或默认配置。
- 不假定固定 Pi 版本；启动时检测可执行文件、版本和 RPC 能力。
- 不兼容时提供可操作诊断，不擅自修复。
- 尽可能复用用户已经配置的 Pi 行为。

### 8.3 会话与安全

- 每个 Pi 会话只绑定一个工作区。
- 启动时以工作区根目录作为稳定 `cwd`，会话中不动态切换。
- 从全局 Homepage 创建 Pi 会话时必须先选定工作区。
- 跨工作区内容只能作为显式上下文附加，不改变文件操作边界。
- 用户配置的 Pi 是独立可信边界。
- ohMyWork 不拦截或改写 Pi 内部工具行为，只展示过程、支持中止并记录结果。
- Pi 的工具事件不是可靠的执行前审批点。
- ohMyWork 自身未来的自动化授权与 Pi 内部工具权限必须在产品中明确区分。

待定：会话创建/恢复/分支 UX、RPC 崩溃恢复、排队语义、Extension UI 请求映射、历史持久化、WSL/native 可执行文件发现、信任错误提示和兼容版本矩阵。

## 9. 主题系统

- ohMyWork 内部使用稳定的语义主题 Token，不直接把 Zed Schema 当作内部领域模型。
- 通过版本感知的适配器直接导入 Zed Theme Family JSON。
- 支持读取用户现有 Zed 主题，包括 Rainbow 的明暗变体。
- 未知 Zed 字段忽略；缺失的 ohMyWork Token 使用确定性回退。
- 主题变化不能破坏 WCAG 关键状态；需定义警告、修正或安全回退机制。
- 参考的 Zed Theme Schema 当前存在版本演进，例如 `https://zed.dev/schema/themes/v0.2.0.json`，不能假定永久固定。
- Windows Zed 本地主题默认目录：`%USERPROFILE%\AppData\Roaming\Zed\themes\`。

待定：主题扫描目录、手动导入、热重载、实时预览、用户覆盖层、终端/图表/日历语义色映射和不合格对比度处理。

## 10. V2 插件与外部资源方向

### 10.1 插件运行模型

- 插件是独立进程，不把 Rust DLL/CDylib 注入主进程。
- 官方插件优先使用 Rust 编写并分发为独立可执行文件。
- 插件通过带版本的 JSONL/JSON-RPC 类协议、manifest 和能力声明与宿主通信。
- 协议允许未来的非 Rust 实现，但官方实现保持 Rust 优先。
- 插件只扩展资源、触发器、动作、命令和配置 Schema。
- 插件不能注入任意 GPUI 代码；界面由宿主统一渲染。

### 10.2 连接器边界

- 浏览器、邮箱、微信、飞书连接器负责聚合、索引和调度。
- 通过稳定官方 API、深链接或来源动作工作。
- 不重新实现或替代完整来源客户端。
- 对没有稳定接口的动作，保留原始链接并回到来源产品。

### 10.3 资源与自动化（V2 方向，尚未形成最终规格）

- 全局唯一资源信封保存 ID、kind、title、provenance、timestamps、links、capabilities，并保留未经损失的来源 JSON。
- 工作区引用全局资源，不复制资源本体。
- 人工 Markdown/规则/配置使用开放文件；资源状态和运行日志使用 SQLite；大载荷使用普通或内容寻址文件；索引和缓存可重建。
- 自动化规则拟使用 `.ohmywork/rules/*.rule.jsonc`，每条规则一个文件，带 Schema 校验、加载扫描和文件监听；无效规则保持禁用。
- 本地读取/分类动作可自动运行；外部发送、写入、删除默认需要确认，可显式信任。
- 每次运行记录输入快照、结果和失败。

以上 V2 内容保留为方向，不应在 V1 提前固化实现。
